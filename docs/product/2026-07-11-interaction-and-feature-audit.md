# MusicFreeAndroid 交互与功能产品审计

> 文档状态：当前参考
> 适用范围：MusicFreeAndroid 当前交互体验、核心功能闭环与后续产品优先级判断。
> 直接执行：否；本文件是产品审计与排序建议，进入开发前仍需为选定工作项补充或确认设计 spec。
> 当前入口：[DOCS_STATUS](../DOCS_STATUS.md)、[AGENTS](../../AGENTS.md)
> RN 参考：[MusicFree pages](../../../MusicFree/src/pages/)
> 最后校验：2026-07-11

## 1. 审计目的

本次审计回答三个问题：

1. 当前产品是否仍处于“补齐页面和基础功能”阶段。
2. 哪些现有交互会直接破坏用户对产品的信任。
3. 下一阶段应优先优化哪些核心链路，以及哪些新增能力可以暂缓。

审计重点不是重新评价每个页面的视觉风格，而是检查以下产品质量：

- 首次使用是否能顺利完成“安装插件 → 搜索 → 播放”。
- 用户看到的操作是否都能产生明确结果。
- 空态、加载态和错误态是否提供下一步动作。
- 插件差异与失败是否被产品层合理吸收。
- 搜索、播放队列、下载、歌单和推荐能否形成连续闭环。
- 设置项是否容易找到和理解。

## 2. 审计方法与限制

本次结论来自：

- 当前 Android 路由和实际导航挂载。
- 首页、搜索、播放、歌单、下载、插件和设置相关 Compose 实现。
- 当前规范文档及已有产品设计 spec。
- 同级 RN 仓库页面和主要入口。
- 仓库现有首页截图与 GitHub issue 历史。

审计时没有可用的 adb 设备，因此以下内容尚未在真机重新验收：

- 页面转场、返回手势和软键盘交互。
- TalkBack、大字体和系统显示缩放。
- 下载、插件超时和播放失败时的实际等待感受。
- 不同屏幕尺寸下的触控密度和信息拥挤程度。

因此，本文件可以作为产品排序输入，但涉及动效、手势和可访问性的结论应在实现前补一次真机任务流走查。

## 3. 总体判断

MusicFreeAndroid 已经度过“主要页面缺失”的阶段。

当前路由已经覆盖搜索、本地音乐、历史、歌单详情、歌单编辑、推荐歌单、榜单、插件歌单、专辑、歌手、单曲详情、插件管理、下载、自定义主题等主要 RN 页面；Android 侧还额外提供听歌足迹、流量统计、缓存管理、应用更新、桌面歌词和反馈日志能力。路由事实见 [Routes](../../core/src/main/java/com/hank/musicfree/core/navigation/Routes.kt) 和 [AppNavHost](../../app/src/main/java/com/hank/musicfree/navigation/AppNavHost.kt)。

下一阶段的核心矛盾已经从“有没有功能”转为：

- 新用户不知道从哪里开始。
- 相同操作在不同页面的行为不一致。
- 部分可见操作没有实际结果。
- 产品直接暴露插件结构，用户需要理解平台和插件差异。
- 设置和诊断能力持续增加，但信息架构仍是长列表。

产品方向应从“继续增加独立页面”切换为“降低插件型播放器的使用成本，并打磨搜索到播放的核心闭环”。

## 4. 当前值得保留的产品基础

### 4.1 RN 主要能力已经基本覆盖

Android 当前不仅具备 RN 的主要消费页面，也已经补齐 `downloading` 和 `setCustomTheme`。旧文档中“缺少这两个页面”的描述不再适用于当前代码。

### 4.2 播放、歌词和运行态基础较完整

当前已经具备：

- 播放队列、播放模式、通知栏与冷启动恢复。
- 歌词自动搜索、手动关联、本地导入、翻译和偏移调整。
- 当前播放歌曲行状态和定位到当前歌曲。
- 播放失败换源、播放/下载音质回退等策略设置。

后续不应为视觉改版破坏这些已经建立的运行态和播放器约束。

### 4.3 Android 本地增强形成差异化基础

听歌足迹、流量统计、在线播放缓存管理、桌面歌词和日志反馈，已经让 Android 版本不再只是 RN 页面复刻。这些能力适合继续向“可解释推荐”“插件健康状态”和“用户可控的数据管理”演进。

## 5. 优先级结论

| 优先级 | 工作项 | 用户影响 | 预计工作量 |
|---|---|---|---|
| P0 | 修复详情列表“下一首播放”空操作 | 高：可见操作无结果，直接损害信任 | 小 |
| P0 | 移除或实现下载任务整行点击 | 中高：当前存在虚假可点击反馈 | 小 |
| P1 | 首次使用引导与可操作空态 | 高：决定用户能否完成首次在线播放 | 中 |
| P1 | 综合搜索与插件健康状态 | 高：降低插件选择成本，改善失败感知 | 大 |
| P1 | 落地“今日推荐歌单” | 高：形成持续使用和内容发现价值 | 大 |
| P1 | 重构基础设置的信息架构 | 中高：降低设置查找成本 | 中 |
| P2 | 完整下载中心 | 中：补齐下载管理与失败恢复 | 中 |
| P2 | 队列拖拽排序与保存为歌单 | 中：提升重度播放场景效率 | 小到中 |
| P2 | 插件安装可信度与能力预览 | 中：降低未知来源和能力差异风险 | 中 |
| P2 | 听歌数据管理、国际化与无障碍 | 中：提升可控性和长期覆盖面 | 中到大 |

### 5.1 竞品能力筛选后的完全可行工作包

对照网易云音乐与 QQ 音乐后，按“不建设自有后端、不引入账号体系、不修改 PluginApi、不依赖大模型或付费第三方服务”的边界，当前技术方案可以完整承接以下六个工作包：

1. **个性化推荐**：今日推荐歌单、用户偏好调节、本地负反馈、推荐理由、画像查看与清除。
2. **综合搜索**：跨插件增量结果、同歌去重、最佳来源选择、插件健康状态与单来源重试。
3. **场景发现**：通勤、学习、运动、睡前等场景歌单，以及语种、曲风和软标签入口。
4. **听歌回顾**：周报、月报、年度报告、那年今日、曲风变化、听歌时段和分享卡片。
5. **内容氛围**：评论分页、热评展示、评论卡片，以及歌词多选海报分享。
6. **播放与基础体验**：队列拖拽、保存队列为歌单、首次插件安装引导、可操作空态和设置搜索。

以下能力不纳入“完全可行”范围：私人漫游、智能随机、AI Agent、一起听、听歌识曲、智能混音、写评论与实时多设备同步。它们仍依赖更高质量的单曲候选、服务端、模型、统一身份或播放器架构扩展。

### 5.2 第一项实施选择：今日推荐歌单

2026-07-11 确认先实施“今日推荐歌单”。实施以 [听歌偏好推荐歌单设计](../superpowers/specs/2026-07-04-listening-preference-recommendation-design.md) 为当前规范，边界如下：

- 使用 `listen_event` 在 Android 本地生成偏好画像。
- 通过现有推荐 tag 与 `search(..., "sheet")` 获取候选，不新增插件接口。
- 候选去重、排序、推荐理由和每日快照全部在 Android 本地完成。
- 不建设推荐后端，不向插件传递用户画像。
- 完全离线时只展示已缓存快照；生成新结果仍依赖现有插件网络。
- 第一版只推荐歌单，不同时实现私人 FM、单曲推荐或大模型能力。

## 6. P0：必须先修的信任问题

### 6.1 详情列表“下一首播放”是空操作

歌单详情、插件歌单详情和榜单详情都向用户展示“下一首播放”，但对应分支仍是空实现或 TODO：

- [PlaylistDetailScreen](../../feature/home/src/main/java/com/hank/musicfree/feature/home/playlist/PlaylistDetailScreen.kt)
- [PluginSheetDetailScreen](../../feature/home/src/main/java/com/hank/musicfree/feature/home/pluginsheet/PluginSheetDetailScreen.kt)
- [TopListDetailScreen](../../feature/home/src/main/java/com/hank/musicfree/feature/home/toplist/TopListDetailScreen.kt)

搜索页和播放页已经能正常调用 `PlayerController.addNextInQueue()`，说明这不是播放器能力缺失，而是详情页面接线不完整。

建议：

- 所有入口统一调用同一个加入下一首 action。
- 成功后展示“已加入下一首播放”。
- 如果目标歌曲已经是当前歌曲，应给出明确反馈，不静默无效。
- 加入后队列页立即可见，行为在所有歌曲列表保持一致。

验收标准：

- 歌单、榜单、插件歌单和搜索结果中的相同操作具有相同行为。
- 点击后队列中下一项为目标歌曲。
- 重复加入、当前歌曲和空队列场景均有确定行为。

### 6.2 下载任务行存在虚假点击反馈

[DownloadingScreen](../../feature/home/src/main/java/com/hank/musicfree/feature/home/downloading/DownloadingScreen.kt) 给进行中任务整行添加了点击与日志，但实际 `onClick` 为空。

短期建议：移除整行点击态，只保留取消按钮。

完整方案：点击任务进入任务详情或展开区域，展示：

- 插件来源、歌曲 ID 和请求音质。
- 下载速度、已下载大小、预计总大小。
- 保存目录。
- 失败原因和恢复动作。

## 7. P1：下一阶段主产品工作

### 7.1 首次使用引导与可操作空态

插件订阅当前默认为空。用户未安装插件时，搜索、推荐歌单和榜单页面只展示“请先在设置中安装插件”，没有直接操作入口：

- [SearchScreen](../../feature/search/src/main/java/com/hank/musicfree/feature/search/SearchScreen.kt)
- [RecommendSheetsScreen](../../feature/home/src/main/java/com/hank/musicfree/feature/home/recommendsheets/RecommendSheetsScreen.kt)
- [TopListScreen](../../feature/home/src/main/java/com/hank/musicfree/feature/home/toplist/TopListScreen.kt)

这段提示还存在信息不准确：插件管理是首页侧栏独立入口，不是基础设置页面中的明显子项。

建议首次使用流程：

1. 首页展示轻量引导卡，解释在线搜索依赖音乐源插件。
2. 主按钮使用“安装音乐源插件”，直接进入插件管理。
3. 插件页提供“粘贴订阅地址”“从网络安装”“从文件导入”三条清晰路径。
4. 安装成功后提供“去搜索”按钮，完成闭环。
5. 权限只在实际使用对应功能时请求，不在首次启动集中索取。

所有空态应采用“说明 + 主操作 + 可选帮助”的结构：

| 场景 | 主操作 |
|---|---|
| 没有插件 | 安装插件 |
| 没有歌单 | 新建歌单 / 导入歌单 |
| 没有搜索结果 | 修改关键词 / 切换来源 |
| 没有下载任务 | 去搜索歌曲 |
| 插件不支持榜单 | 切换插件 / 管理插件 |
| 推荐生成失败 | 重试 / 使用上次结果 |

建议指标：

- 首次启动到首次成功播放的中位时间。
- 进入无插件空态后成功进入插件管理的比例。
- 安装插件后 10 分钟内完成首次搜索和播放的比例。

### 7.2 增加默认“综合搜索”

当前搜索结果使用“媒体类型 Tab × 插件 Tab”组织。该结构保留了插件可控性，但把平台选择成本直接交给用户。

建议在现有结构上增加默认“综合”场景：

- 多插件结果按完成顺序增量展示，不等待慢插件。
- 按规范化歌曲名和主歌手合并重复歌曲。
- 综合结果优先选择近期成功率高、延迟低且能提供目标音质的来源。
- 播放失败时可尝试同一歌曲的其他来源。
- 原有插件 Tab 继续保留，供用户精确选择来源。
- 结果行展示当前选择的来源，但不要求用户预先理解插件能力。

同时增加插件健康状态：

- 正常、较慢、近期失败、加载错误、已禁用。
- 最近更新时间和最近一次成功调用时间。
- 单插件重试、临时跳过和进入插件管理。

综合搜索不能重新引入“等待所有插件”的问题；慢插件必须只影响自己的状态。

### 7.3 落地“今日推荐歌单”

[听歌偏好推荐歌单设计](../superpowers/specs/2026-07-04-listening-preference-recommendation-design.md) 已明确本地画像、候选召回、本地排序、每日快照和降级边界，但生产代码尚未落地对应能力。

第一版建议保持设计边界：

- 首页增加“今日推荐”轻入口。
- 只推荐歌单，不同时启动单曲推荐或私人 FM。
- 使用本地听歌事件构建画像，不向插件传递用户画像。
- 推荐结果展示真实、可解释的理由。
- 低样本时提示“多听一些，推荐会更准”。
- 支持“换一批”“少推荐此类”和关闭个性化。
- 保留上一次成功快照，部分插件失败时仍可展示可用结果。

建议指标：

- 推荐入口点击率。
- 推荐歌单详情打开率。
- 推荐歌单首次播放率。
- “换一批”和负反馈比例。
- 推荐生成成功率及每个插件的失败占比。

### 7.4 重构基础设置的信息架构

[BasicSettingsContent](../../feature/settings/src/main/java/com/hank/musicfree/feature/settings/BasicSettingsContent.kt) 当前约有 46 个设置条目、9 个分区，桌面歌词细节参数和开发诊断能力都位于同一长列表中。

建议改为分类首页：

- 播放与音质。
- 下载与存储。
- 歌词与桌面歌词。
- 网络与更新。
- 缓存与数据。
- 高级与诊断。

交互建议：

- 顶部提供设置搜索。
- 分类首页只展示常用状态摘要。
- 桌面歌词的对齐、位置、宽度、字号和颜色进入独立详情页。
- “开发选项”默认放入“高级与诊断”，不与普通设置混排。
- 清理类操作展示预计影响范围和可释放空间。
- 互相依赖的设置使用条件显示，而不是让不可用项长期占位。

## 8. P2：后续补强方向

### 8.1 完整下载中心

建议从当前“进行中 + 失败”扩展为：

- 进行中：暂停、恢复、取消、速度和剩余大小。
- 失败：原因分类、直接修复入口和批量重试。
- 已完成：播放、查看文件、加入歌单、删除文件。

当失败原因为权限、移动网络限制或存储目录失效时，应直接提供相应设置入口，而不是只展示错误文字。

### 8.2 播放队列拖拽与保存

[PlayQueue](../../player/src/main/java/com/hank/musicfree/player/queue/PlayQueue.kt) 已具备 `move(fromIndex, toIndex)`，但 [PlayQueueSheetContent](../../feature/player-ui/src/main/java/com/hank/musicfree/feature/playerui/component/queue/PlayQueueSheetContent.kt) 目前只提供播放和删除。

建议补充：

- 长按拖拽排序。
- 保存当前队列为新歌单。
- 多选删除或批量加入歌单。
- 清空队列前确认，当前正在播放时明确后续状态。

### 8.3 插件安装可信度与能力预览

[PluginListScreen](../../feature/settings/src/main/java/com/hank/musicfree/feature/settings/pluginlist/PluginListScreen.kt) 当前从网络安装时，输入 URL 后直接进入安装。

建议增加安装预览：

- 插件名称、平台、版本和来源域名。
- 支持搜索、歌词、榜单、推荐歌单、导入等能力。
- 是否需要用户变量。
- 更新时展示版本变化和能力变化。
- 来源异常、重复平台或版本不兼容时明确说明后果。

### 8.4 听歌数据管理

在继续建设画像和推荐前，应提供：

- 清除听歌足迹。
- 导出听歌数据。
- 关闭听歌统计或个性化推荐。
- 说明数据只保存在本地，以及哪些备份会包含这些数据。

### 8.5 国际化、可访问性与大屏适配

当前用户文案大量硬编码为中文。后续建议：

- 逐步迁移到字符串资源，不要求一次性全量改造。
- 使用 TalkBack 验证搜索、歌曲菜单、播放控制和拖拽替代操作。
- 验证系统大字体下的首页快捷入口、歌曲行和设置值。
- 验证平板或横屏下是否需要双栏设置和列表详情布局。

## 9. 暂不建议优先投入的方向

在首次使用、综合搜索和操作一致性尚未完成前，暂不建议优先建设：

- 大规模视觉风格重做。
- 低对比度的新拟态视觉。
- 私人 FM、复杂机器学习推荐。
- Chromecast、DLNA、Android Auto 等新终端形态。
- 云账号和跨设备同步体系。
- 均衡器、音效市场等重型播放增强。

这些能力并非没有价值，但会扩大维护面，且不能解决当前最核心的“用户能否快速找到并稳定播放音乐”。

## 10. 推荐执行顺序

### 阶段一：修复信任问题

1. 接通所有“下一首播放”。
2. 移除下载任务虚假点击或补任务详情。
3. 统一相关成功、失败和重复操作反馈。

### 阶段二：降低首次使用成本

1. 无插件空态直达插件管理。
2. 插件安装后直达搜索。
3. 补歌单、下载、榜单和推荐页的可操作空态。

### 阶段三：优化内容发现

1. 综合搜索与去重。
2. 插件健康状态与失败恢复。
3. 今日推荐歌单 MVP。

### 阶段四：提升重度使用效率

1. 设置分类与搜索。
2. 完整下载中心。
3. 队列拖拽和保存为歌单。
4. 听歌数据管理和可访问性专项。

## 11. 后续决策要求
